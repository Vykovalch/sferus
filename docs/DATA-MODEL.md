# Модель данных — v1 «Каталог»

Финальная модель, утверждённая до написания миграций. Источник истины для `src/lib/db/schema.ts`.

При расхождении документа и кода — **прав код**, а документ нужно поправить. Не наоборот:
это описание принятых решений, а не второй источник истины о структуре таблиц.

---

## Область v1

**Внутри:** каталог услуг · доска заданий · публичные профили · раскрытие контактов ·
избранное (услуги и задания) · модерация в админке

**Вне v1:** отклики · отзывы · рейтинги · чат · заказы · платежи

Связь между пользователями происходит **только через раскрытие контактных данных**.
Платформа не наблюдает сделку и не знает о факте выполнения работы — из этого следует
почти всё остальное в модели: отсутствие статуса `in_progress` у заданий, отсутствие
проверяемых отзывов, отсутствие связи «задание → исполнитель».

### Пользователь универсален

Отдельных ролей «заказчик» и «исполнитель» не существует. Один и тот же пользователь
одновременно публикует услуги, создаёт задания и пользуется платформой в обеих ипостасях.

> **Не путать с `profiles.type`.** Поле `type` (`individual` / `company`) описывает
> **правовую форму** — частное лицо или компания. Это не роль. Оно нужно фильтру
> «Исполнитель» в каталоге и бейджам на карточках.

Следствие: константа `USER_ROLES` (`CLIENT` / `EXECUTOR` / `BOTH`) в `lib/constants.ts`
и колонка «роль» в админке **теряют смысл** и подлежат удалению.

### Модель доверия в v1

Отзывов нет, поэтому доверие строится на трёх сигналах: **бейдж «Проверенный»**,
**опыт работы**, **заполненность профиля**. Это делает `isVerified` не украшением,
а основным инструментом — см. открытый вопрос 1.

## Enum-типы

| Тип | Значения |
|---|---|
| `profile_type` | `individual` · `company` |
| `contact_channel` | `phone` · `whatsapp` · `telegram` · `viber` |
| `price_unit` | `hour` · `job` · `day` · `sqm` · `unit` |
| `moderation_status` | `pending` · `approved` · `rejected` · `blocked` |
| `task_status` | `open` · `completed` · `cancelled` |

### Семантика `moderation_status`

| Значение | Смысл | Используется в v1 |
|---|---|---|
| `pending` | ожидает модерации | нет — задел на премодерацию |
| `approved` | допущено к публикации | ✅ значение по умолчанию |
| `rejected` | не прошло модерацию | нет — задел на премодерацию |
| `blocked` | опубликованное объявление заблокировано администратором | ✅ основной админский сценарий |

**`approved` по умолчанию — постмодерация, решение утверждено.** Объявление попадает в
каталог сразу после публикации и базовых автоматических проверок (в v1 это zod-валидация);
администратор при необходимости переводит его в `blocked` позже.

`approved` означает «допущено к публикации», **а не «лично проверено администратором»** —
формулировка важна, чтобы статус не путали с бейджем доверия.

Значение `pending` по умолчанию означало бы, что ничего не видно до ручного одобрения,
а штата модераторов нет — каталог встал бы в день запуска. Премодерация в v1 не
реализуется; переход на неё позже — смена значения по умолчанию, без изменения структуры.

`pending` и `rejected` включены в enum заранее намеренно: добавление значения задним
числом требует `ALTER TYPE ... ADD VALUE`, которое в старых версиях PostgreSQL не
выполняется внутри транзакции. Сейчас это бесплатно.

Доступность объявления определяется строгим равенством `moderationStatus = 'approved'`,
поэтому появление новых значений не потребует правки предиката в запросах.

### `categories`

Плоский список категорий. Единственный источник данных о категориях.

| `type` | `profile_type` default `individual` | ✅ | **новое** |
| `bio` | text | | есть |
| `avatar` | text | | есть, **подлежит удалению** — см. ниже |
| `cityId` | bigint → `cities.id` | | есть |
| `experienceYears` | integer | | **новое** |
| `isVerified` | boolean default false | ✅ | **новое** |

**Связи:** → `user`, `cities` · ← `profile_contacts`, `services`, `tasks`, `favorites`
**Статусы:** `type`, `isVerified`
**Индексы:** `(username)`, `(cityId)`

**`username` в v1 не редактируется.** Он генерируется при регистрации из имени
(`lib/username.ts`) и остаётся адресом публичной страницы навсегда — смена имени его
не меняет. Редактирование потребовало бы проверки уникальности, списка зарезервированных
слов и решения о судьбе старых ссылок; ни одно из этого не окупается, пока платформа
не запущена. Возвращаемся к вопросу вместе с редиректами со старых адресов.

**Аватар: источник истины — `user.image`, а не `profiles.avatar`.** Решение принято
на этапе 1.3. Причины: `user.image` заполняет better-auth при входе через Google,
меняется он тем же `updateUser`, что и имя, и — главное — приходит внутри сессии,
поэтому шапка рисует аватар без единого дополнительного запроса. Своя колонка дала бы
второе значение того же поля и вечный вопрос «какое из двух показывать»; отдельная
колонка ради «переопределить картинку из OAuth» не нужна: `updateUser` перезаписывает
`image` напрямую, а better-auth по умолчанию не затирает его при повторных входах.

`profiles.avatar` **удаляется** — вместе с работами по загрузке изображений на этапе 2,
когда появится хранилище и код, который вообще пишет аватар. Сейчас колонка пуста
и не читается ни одним запросом, отдельная миграция ради неё не оправдана.

### `profile_contacts` — новая

Каналы связи с индивидуальной видимостью. Единый механизм для услуг **и** заданий:
контакты берутся из профиля владельца объявления.

| Поле | Тип | Обяз. |
|---|---|---|
| `id` | bigint identity PK | ✅ |
| `profileId` | bigint → `profiles.id` cascade | ✅ |
| `channel` | `contact_channel` | ✅ |
| `value` | text | ✅ |
| `isVisible` | boolean default true | ✅ |

**Связи:** → `profiles`
**Ограничения:** `UNIQUE(profileId, channel)`

Отдельная таблица, а не четыре колонки в `profiles`: форма настройки контактов даёт
чекбокс включения **на каждый канал**, то есть колоночный вариант — это восемь колонок,
и каждый новый канал требует миграции.

Выборка контактов — всегда `WHERE isVisible = true` **и только после проверки сессии
на сервере** (см. ARCHITECTURE.md, раздел 8).

**Как каналы заполняются в v1 (этап 1.3).** Форма спрашивает **один** номер телефона
и три галочки к нему — звонки, WhatsApp, Viber: мессенджеры работают по тому же номеру.
В таблице это три строки с одинаковым `value` и собственным `isVisible` у каждой.
Telegram — отдельное поле и четвёртая строка, там имя пользователя, а не номер.
Значения enum используются все четыре.

`isVisible = false` **сохраняет** значение: снятая галочка прячет контакт, а не удаляет
его. Строка исчезает только когда поле очищено — пустое значение в колонке `NOT NULL`
смысла не имеет. Это и есть причина, по которой контакты вынесены в таблицу.

### `favorites` — новая

Избранное. Хранит **и услуги, и задания** в одной таблице.

| Поле | Тип | Обяз. |
|---|---|---|
| `id` | bigint identity PK | ✅ |
| `userId` | text → `user.id` cascade | ✅ |
| `serviceId` | bigint → `services.id` cascade | |
| `taskId` | bigint → `tasks.id` cascade | |
| `createdAt` | timestamp default now | ✅ |

**Ограничения:**
```sql
CHECK ( (service_id IS NOT NULL AND task_id IS NULL)
     OR (service_id IS NULL AND task_id IS NOT NULL) )

UNIQUE INDEX (user_id, service_id) WHERE service_id IS NOT NULL
UNIQUE INDEX (user_id, task_id)    WHERE task_id    IS NOT NULL
```
**Индексы:** `(userId, createdAt DESC)`

**Почему одна таблица с двумя nullable-ссылками, а не две таблицы.** Раздел «Избранное»
показывает оба типа вперемешку с фильтром по типу. При одной таблице это один запрос с
сортировкой по дате; при двух пришлось бы делать `UNION` и объединять пагинацию.
`CHECK` гарантирует, что заполнена ровно одна ссылка, а обе связи — настоящие внешние
ключи с каскадным удалением, так что целостность не страдает.

**Почему не `entityType` + `entityId` без внешних ключей.** Классическая полиморфная
связь выглядит гибче, но лишает базу возможности проверять ссылки: при удалении
объявления в избранном останется строка, указывающая в пустоту, и чинить это придётся
кодом. Две настоящие связи с каскадом дешевле любой гибкости, которая здесь не нужна.

### Недоступные объявления в избранном

Требование: если сохранённое объявление отключил автор или заблокировал администратор,
оно **остаётся** в избранном пользователя с пометкой о недоступности, но исчезает из
каталога и публичных списков.

**Дополнительных колонок для этого не нужно.** Отключение и блокировка — это изменение
состояния, а не удаление строки: строка объявления остаётся на месте, поэтому запись в
избранном сохраняется сама собой. Доступность вычисляется в запросе:

```
услуга доступна  ⟺  isActive = true   AND moderationStatus = 'approved'
задание доступно ⟺  status   = 'open' AND moderationStatus = 'approved'
```

Каталог фильтрует по этому предикату, избранное возвращает его как флаг и рисует плашку
«объявление недоступно». Один предикат, два разных применения.

**Soft delete (`deletedAt`) рассмотрен и отклонён.** Он заставил бы дописывать
`WHERE deleted_at IS NULL` в каждый запрос проекта навсегда, тогда как требование
говорит об *отключено* и *закрыто*, а не об *удалено*. Постоянная цена за случай,
которого в требовании нет.

**Единственный случай, когда запись из избранного исчезает** — физическое удаление
объявления по каскаду. Отсюда разделение инструментов администратора:

| Действие в админке | Эффект | Судьба избранного |
|---|---|---|
| «Скрыть» | `moderationStatus = 'blocked'` | сохраняется, показано как недоступное |
| «Удалить» | физический `DELETE` | удаляется каскадом |

«Скрыть» — основной и обратимый инструмент. «Удалить» предназначено для спама и
противоправного контента, где содержимое обязано исчезнуть везде, включая чужое
избранное; каскад здесь и есть желаемое поведение.

У автора удаления в v1 нет — в дашборде только переключатель активности.

Цена решения: добавление третьего типа избранного потребует ещё одной колонки и правки
`CHECK`. При таком росте разумно вернуться к обсуждению — но для двух типов это дешевле
альтернатив.

## Отложено

Спецификации зафиксированы, чтобы вернуться без повторного проектирования.

### `responses` (после v1)
`id` · `taskId → tasks` · `userId → user` · `message` · `price` nullable ·
`status` (`pending` / `accepted` / `rejected` / `withdrawn`) · `createdAt` · `updatedAt`
`UNIQUE(taskId, userId)` — один отклик на задание от пользователя.
Правила: нельзя откликаться на своё задание и на задание не в статусе `open`.
Возвращает в жизненный цикл заданий статус `in_progress` и связь «задание → исполнитель».

### `reviews` (после `responses`)
`id` · `authorId → user` · `targetId → user` · `taskId → tasks` · `rating` 1–5 ·
`comment` · `createdAt`
`taskId` — источник легитимности: отзыв возможен только по завершённому заданию.
Вводить отзывы **до** появления откликов не следует: без привязки к сделке они
превращаются в свободную форму, которая тривиально накручивается, а репутация на
маркетплейсе и есть продукт.

### Аналитика просмотров (после v1)
Счётчика просмотров в схеме нет **намеренно**. Наивный `viewsCount++` на каждом открытии
страницы считает ботов, поисковых роботов и перезагрузки владельцем собственного
объявления — то есть даёт исполнителю заведомо завышенное число, на которое он не может
опереться. Возвращаемся к вопросу, когда будет определена корректная модель подсчёта
(дедупликация по сессии, отсечение владельца и краулеров, отдельная таблица событий).

### Прочее
Продвижение «Топ» (`isPromoted`, `promotedUntil`) · счётчик раскрытий контактов ·
настройки уведомлений · денормализованный рейтинг · срок выполнения задания ·
`width` / `height` у изображений · `isActive` у справочников · чат · заказы · платежи

## Открытые вопросы

### 1. Что означает «Проверенный»

`isVerified` остаётся в схеме, но **критерий не зафиксирован**. Поскольку отзывов в v1
нет, это главный сигнал доверия, и произвольная выдача бейджа обесценит его в первый же
месяц. Нужно определить до реализации профилей: кто ставит, на основании чего
(подтверждённый телефон? документы? проверка администратором вручную?), можно ли снять.

### 2. Денежный тип

`price` и `budget` предложены как `integer`: для рублей ПМР потолка в 2.1 млрд
достаточно, а `bigint` в JS-режиме Drizzle тянет лишние преобразования. Если суммы
могут быть с копейками — нужен `numeric(10,2)`.
