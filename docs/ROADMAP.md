# Дорожная карта Sferus

Порядок работ от текущего состояния до production. Внутри этапа пункты можно
переставлять; **этапы менять местами нельзя** — каждый следующий опирается на предыдущий.

Текущее фактическое состояние — в [PROGRESS.md](PROGRESS.md).
Утверждённая модель данных — в [DATA-MODEL.md](DATA-MODEL.md).

Принцип: **вертикальные срезы, а не горизонтальные слои.** Одна фича доводится от схемы
БД до работающего UI целиком, прежде чем начинается следующая. Это даёт проверяемый
результат на каждом шаге вместо «всё готово на 80%».

---

## Объём v1

**v1 — это каталог услуг и доска заданий без внутреннего взаимодействия.**
Связь между пользователями происходит только через раскрытие контактных данных.

Вне v1: отклики · отзывы · рейтинги · чат · заказы · платежи.

Решение зафиксировано в [DATA-MODEL.md](DATA-MODEL.md) вместе с сохранёнными
спецификациями отложенных сущностей.

## Этап 0 — Фундамент

Блокирует всё остальное. Пока не закрыт, писать бизнес-логику нельзя: любая фича упрётся
либо в отсутствующие колонки, либо в отсутствующую валидацию.

### 0.1. Миграция схемы БД

Полная спецификация — в [DATA-MODEL.md](DATA-MODEL.md). Кратко:

**Создать:** `profile_contacts`, `service_images`, `favorites` (услуги и задания в одной
таблице), пять enum-типов.

**Удалить:** таблицы `responses` и `reviews` (вне v1, пустые — спецификации сохранены),
`profiles.phone`, `services.image`.

**Дополнить:** `services` — `priceUnit`, `homeVisit`, `isNegotiable`, `moderationStatus`,
`updatedAt` · `tasks` — `isNegotiable`, `moderationStatus`, `updatedAt` · `profiles` —
`type`, `experienceYears`, `isVerified`, `updatedAt`.

Заодно, пока таблицы пустые:

- **Индексы на доменных таблицах.** В `auth-schema.ts` они есть, в `schema.ts` — нет
  ни одного. Список — в DATA-MODEL.md по каждой таблице.
- **`userId` сделать `notNull`** в `services` и `tasks`. Сейчас nullable — объявление
  без владельца не должно быть выразимо в принципе.
- **`tasks.status` → enum** `open` / `completed` / `cancelled`. Сейчас `integer default 1`
  без маппинга где-либо.
- **`price` и `budget` → nullable `integer`** плюс `isNegotiable` и CHECK-ограничение.

### 0.2. Переезд на структуру `features/`

Все импорты идут через `@/`, риск низкий. Делается **до** написания логики — потом
переезд станет заметно дороже.

## Этап 1 — Ядро MVP

Первая фича задаёт образец для всех последующих. **Услуги делаются первыми** — там самая
проработанная форма и меньше всего связей с другими сущностями. Ревью первого среза
проводим особенно внимательно: дальше по этому шаблону пойдёт всё остальное.

### 1.1. Услуги — полный вертикальный срез

- `features/services/schemas.ts` — `createServiceSchema`, `updateServiceSchema`
- `features/services/actions.ts` — создание, редактирование, снятие с публикации
- `features/services/queries.ts` — список с фильтрами, карточка, «мои услуги»
- Подключить `CreateServiceForm` к action через `useActionState`
- Заменить моки на страницах списка, детальной и в дашборде

### 1.2. Задания

Аналогично услугам: схемы, actions, queries, подключение `CreateTaskForm`,
замена моков на `/tasks`, `/tasks/[id]` и в дашборде.

Плюс приведение UI к модели v1: убрать поле «Срок выполнения», убрать статус
`in_progress` из `StatusFilter` и `TaskCard`, заменить `done` на `completed`.

### 1.3. Профиль, контакты и раскрытие

- Сохранение профиля и контактных каналов (`profile_contacts`)
- Публичная страница `/profiles/[username]` на реальных данных
- **Раскрытие контактов по правилу из ARCHITECTURE.md, раздел 8** — контакты не должны
  попадать в payload неавторизованному пользователю
- Единый механизм раскрытия для услуг **и заданий** — на странице задания появляется
  кнопка «Показать контакты заказчика» вместо «Откликнуться»

Это центральная фича v1: без откликов раскрытие контактов — **единственный** способ
связи между пользователями на платформе.

### 1.4. Избранное

- Таблица `favorites` для услуг и заданий, привязка к пользователю вместо `useState`
- Раздел «Избранное» с фильтром по типу объявления

## Этап 3 — Готовность к production

- **Поиск и фильтрация** через searchParams вместо статичной разметки
- **Пагинация** на реальных запросах
- **Тесты критичных путей**: регистрация, создание объявления, раскрытие контактов.
  Полное покрытие не нужно — нужны те сценарии, поломка которых означает потерю денег
  или утечку данных
- **Наблюдаемость**: логирование ошибок, минимальный мониторинг
- **SEO**: динамические метаданные для страниц услуг и заданий, sitemap
- **Аудит безопасности перед запуском** — отдельная проверка каждого Server Action на
  наличие всех трёх проверок из правила 3.3

## После v1

Отложено сознательно, спецификации сохранены в [DATA-MODEL.md](DATA-MODEL.md).
Порядок важен: отзывы без откликов не имеют якоря легитимности.

1. **Отклики** (`responses`) — возвращают в жизненный цикл заданий статус `in_progress`
   и связь «задание → исполнитель». Принятие отклика — первая мутация нескольких таблиц
   сразу, здесь проверяется вопрос транзакций из ARCHITECTURE.md, 9.1
2. **Отзывы и рейтинги** — только после откликов, с привязкой к завершённому заданию
3. Продвижение объявлений «Топ», аналитика просмотров и раскрытий контактов

## Вне дорожной карты

Сознательно не планируется на текущем горизонте. Зафиксировано, чтобы не всплывало как
«а давайте ещё»:

- Платежи и escrow
- Заказы как отдельная сущность
- Чат между пользователями
- Мобильное приложение
- Мультиязычность (проект русскоязычный по продуктовому решению)
- Уведомления в реальном времени
