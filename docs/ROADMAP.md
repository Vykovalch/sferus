# Дорожная карта Sferus

Порядок работ от текущего состояния до production. Внутри этапа пункты можно
переставлять; **этапы менять местами нельзя** — каждый следующий опирается на предыдущий.

Текущее фактическое состояние — в [PROGRESS.md](PROGRESS.md).
Утверждённая модель данных — в [DATA-MODEL.md](DATA-MODEL.md).

Принцип: **вертикальные срезы, а не горизонтальные слои.** Одна фича доводится от схемы
БД до работающего UI целиком, прежде чем начинается следующая. Это даёт проверяемый
результат на каждом шаге вместо «всё готово на 80%».

---

## Объём v1

**v1 — это каталог услуг и доска заданий без внутреннего взаимодействия.**
Связь между пользователями происходит только через раскрытие контактных данных.

Вне v1: отклики · отзывы · рейтинги · чат · заказы · платежи.

Решение зафиксировано в [DATA-MODEL.md](DATA-MODEL.md) вместе с сохранёнными
спецификациями отложенных сущностей.

Решения, принятые по ходу и заслуживающие внимания при чтении кода:

- **`zod` поставлен явно четвёртой версией.** Транзитивно наверх поднималась третья
  от `shadcn`, тогда как `better-auth` работает на четвёртой. После явной установки
  дерево дедуплицировалось.
- **Проверка прав на объект не обобщена** в `authedAction` — она остаётся явной строкой
  в теле каждого действия. Обоснование в JSDoc функции.
- **Цвета категорий живут в коде, не в БД**: они относятся к дизайн-системе, и
  Tailwind-классы из базы не попадают в сборку CSS.
- **CI проверяет форматирование только у изменённых файлов** (`biome ci --changed`).
  Легаси написано до появления конфига Biome и расходится с ним примерно в 130 местах;
  разовое форматирование всего репозитория отложено, стандарт применяется к тому,
  что реально правят.
- **`.gitattributes` фиксирует LF** — иначе на Windows локальный Biome видел на 42
  ошибки больше, чем CI на Linux.

Незакрытым из этапа 0 не осталось ничего.

проводим особенно внимательно: дальше по этому шаблону пойдёт всё остальное.

## Этап 3 — Готовность к production

- **Поиск и фильтрация** через searchParams вместо статичной разметки
- **Пагинация** на реальных запросах
- **Тесты критичных путей**: регистрация, создание объявления, раскрытие контактов.
  Полное покрытие не нужно — нужны те сценарии, поломка которых означает потерю денег
  или утечку данных
- **Наблюдаемость**: логирование ошибок, минимальный мониторинг
- **SEO**: динамические метаданные для страниц услуг и заданий, sitemap
- **Аудит безопасности перед запуском** — отдельная проверка каждого Server Action на
  наличие всех трёх проверок из правила 3.3

## После v1

Отложено сознательно, спецификации сохранены в [DATA-MODEL.md](DATA-MODEL.md).
Порядок важен: отзывы без откликов не имеют якоря легитимности.

1. **Отклики** (`responses`) — возвращают в жизненный цикл заданий статус `in_progress`
   и связь «задание → исполнитель». Принятие отклика — первая мутация нескольких таблиц
   сразу, здесь проверяется вопрос транзакций из ARCHITECTURE.md, 9.1
2. **Отзывы и рейтинги** — только после откликов, с привязкой к завершённому заданию
3. Продвижение объявлений «Топ», аналитика просмотров и раскрытий контактов

## Вне дорожной карты

Сознательно не планируется на текущем горизонте. Зафиксировано, чтобы не всплывало как
«а давайте ещё»:

- Платежи и escrow
- Заказы как отдельная сущность
- Чат между пользователями
- Мобильное приложение
- Мультиязычность (проект русскоязычный по продуктовому решению)
- Уведомления в реальном времени
