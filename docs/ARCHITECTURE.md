# Архитектура Sferus

Документ описывает, как устроен проект и почему именно так. Решения приняты до начала
разработки бизнес-логики — осознанно, чтобы не переделывать позже.

> **Внимание при работе с Next.js.** `AGENTS.md` предупреждает, что версия Next.js в
> проекте содержит breaking changes относительно распространённых знаний. Примеры кода
> ниже иллюстрируют **структуру и границы слоёв**, а не точные сигнатуры API. Перед
> написанием кода сверяйся с `node_modules/next/dist/docs/`.

---

## 1. Общий принцип

Приложение состоит из трёх слоёв. Поток данных строго однонаправленный.

```
Чтение:   Server Component  →  queries.ts  →  Drizzle  →  Postgres
Запись:   Client Component  →  Server Action  →  Drizzle  →  Postgres
                                    ↓
                             revalidatePath
```

Нет сервисного слоя. Нет репозиториев. Нет DI-контейнера. Обоснование — раздел 4.

## 2. Структура каталогов

```
src/
  app/                      # ТОЛЬКО роутинг: layout.tsx, page.tsx, route handlers
    (auth)/                 #   вход, регистрация, сброс пароля, верификация
    (main)/                 #   публичная часть + личный кабинет
    admin/                  #   админ-панель (своя проверка роли в layout)
    api/auth/[...all]/      #   catch-all better-auth

  features/                 # ВСЯ бизнес-логика, сгруппирована по домену
    services/
      actions.ts            #   'use server'  — мутации
      queries.ts            #   'server-only' — чтение
      schemas.ts            #   zod-схемы + выведенные типы
      components/           #   UI, принадлежащий только этой фиче
    tasks/
    profiles/               #   профиль + контакты + раскрытие
    categories/             #   справочник: только queries.ts
    cities/                 #   справочник: только queries.ts
    favorites/
    admin/
                            #   responses/ и reviews/ — после v1, см. DATA-MODEL.md

  components/
    ui/                     # shadcn/radix — не трогаем руками
    layout/                 # Header, Footer, MobileMenu, UserMenu
    shared/                 # используется 2+ фичами (SearchBar, CityFilter, ...)

  lib/
    db/
      index.ts              # клиент Drizzle
      schema.ts             # доменные таблицы
      auth-schema.ts        # таблицы better-auth (менять осторожно)
    auth.ts                 # серверная конфигурация better-auth
    auth-client.ts          # клиентские хуки better-auth
    action-client.ts        # authedAction — помечен 'server-only'
    action-state.ts         # контракт ActionState — БЕЗ server-only, см. 5.1
    format.ts               # цены и даты, общее для услуг и заданий
    constants.ts            # иконки и цвета категорий, статусы заданий
    utils.ts                # cn() и мелкие хелперы

  emails/                   # React Email шаблоны
```

**Границей фичи считается сущность БД.** `admin` — отдельная фича, несмотря на работу с
теми же таблицами: у неё другие права доступа и другие запросы.

Состав фич соответствует объёму v1 — см. [DATA-MODEL.md](DATA-MODEL.md).

### Что где лежит — коротко

| Нужно | Файл |
|---|---|
| Прочитать данные для страницы | `features/<domain>/queries.ts` |
| Изменить данные | `features/<domain>/actions.ts` |
| Провалидировать вход формы | `features/<domain>/schemas.ts` |
| Компонент только для этой фичи | `features/<domain>/components/` |
| Компонент для 2+ фич | `components/shared/` |
| Города, категории, статусы | `lib/constants.ts` |

## 3. Правила слоёв

Пять правил. Они не про стиль, а про безопасность и поддерживаемость.

### 3.1. `app/**` не импортирует `db`

Страница делает `await getServiceCards(filters)` и передаёт результат в компоненты.
Никаких `db.select()` внутри `page.tsx`.

Зачем: запрос, живущий в странице, невозможно переиспользовать и невозможно проверить
на утечку полей. Плюс страница перестаёт читаться.

### 3.2. `queries.ts` начинается с `import 'server-only'`

```ts
import 'server-only'
import { db } from '@/lib/db'
```

Зачем: если клиентский компонент случайно импортирует такой модуль, сборка падает с
понятной ошибкой вместо того, чтобы утащить в браузерный бандл клиент БД и строку
подключения. Это дешёвая страховка от дорогой ошибки.

### 3.3. Каждый экспорт из `'use server'` — публичный эндпоинт

Это главное правило документа.

Server Action компилируется в HTTP-эндпоинт с угадываемым идентификатором. Кто угодно
может отправить туда произвольный payload — не только ваша форма и не только через ваш UI.
Поэтому в каждом action, без исключений и в этом порядке:

1. **Аутентификация** — есть ли сессия.
2. **Авторизация** — имеет ли *этот* пользователь право на *этот* объект.
   Владелец услуги? Автор задания? Не забанен?
3. **Валидация** — zod-парсинг входа.

Пункт 2 забывают чаще всего. `deleteService(id)` с проверкой только сессии позволяет
любому авторизованному пользователю удалить чужое объявление.

### 3.4. Query-функции селектят только нужные колонки

```ts
// нет
const rows = await db.select().from(services)

// да
const rows = await db
  .select({ id: services.id, title: services.title, price: services.price })
  .from(services)
```

Зачем — см. раздел 8 про контакты. Коротко: то, что попало в возврат query-функции,
попадает в HTML, отданный браузеру. Скрыть это на клиенте нельзя.

### 3.5. Фичи не импортируют компоненты друг у друга

Если `tasks` понадобился компонент из `services` — это сигнал, что компонент общий.
Переносим в `components/shared/`. Прямой импорт через границу фичи запрещён, иначе через
полгода структура превращается в граф без выраженных модулей.

## 4. Почему нет сервисного слоя

В проекте 7 сущностей и ~9 000 строк кода. **Drizzle сам является слоем абстракции над
SQL** — оборачивать его в репозиторий значит писать код, который только делегирует.
Сервисный слой в проекте такого размера выродится в файлы из одной строки.

Ранняя абстракция — это тоже технический долг, просто он выглядит прилично.

### Порог для усложнения

Извлекаем `features/<domain>/lib/<use-case>.ts`, когда выполнено **любое** из условий:

- action содержит больше ~50 строк оркестрации;
- одна и та же логика нужна в двух и более action;
- логика затрагивает три и более таблицы.

До этого — не усложняем. Правило существует, чтобы усложнение происходило по факту
потребности, а не авансом «на всякий случай».

## 5. Server Actions

Файл: `features/<domain>/actions.ts`.

Чтобы обязательные проверки из правила 3.3 нельзя было забыть, вводится общая обёртка
`lib/action-client.ts` (~40 строк, без внешних зависимостей):

```ts
// Иллюстрация структуры, не готовый код.
// Сигнатуру useActionState сверить с node_modules/next/dist/docs/.

export function authedAction<S extends z.ZodType, R>(
  schema: S,
  handler: (input: z.infer<S>, ctx: { userId: string }) => Promise<R>,
) {
  return async (_prev: ActionState<R>, formData: FormData): Promise<ActionState<R>> => {
    const session = await auth.api.getSession({ headers: await headers() })
    if (!session) return { ok: false, error: 'UNAUTHORIZED' }

    const parsed = schema.safeParse(Object.fromEntries(formData))
    if (!parsed.success) {
      return { ok: false, fieldErrors: z.flattenError(parsed.error).fieldErrors }
    }

    try {
      return { ok: true, data: await handler(parsed.data, { userId: session.user.id }) }
    } catch (e) {
      console.error(e)
      return { ok: false, error: 'INTERNAL' }
    }
  }
}
```

Обёртка закрывает аутентификацию и валидацию. **Авторизацию (права на конкретный объект)
она закрыть не может** — это всегда логика внутри `handler`:

```ts
export const updateService = authedAction(updateServiceSchema, async (input, { userId }) => {
  const owned = await isServiceOwner(input.id, userId)   // ← это не автоматизируется
  if (!owned) throw new ForbiddenError()
  // ...
})
```

Форма возвращаемого состояния совместима с `useActionState` (React 19). Это убирает
ручные `useState(loading)` / `useState(error)`, продублированные сейчас в каждой форме.

### 5.1. Почему контракт состояния вынесен в отдельный модуль

`lib/action-client.ts` помечен `import 'server-only'` — он тянет за собой клиент БД
и работу с сессией. Но `ActionState` и `idleState` нужны **клиентским** компонентам:
без них не вызвать `useActionState`.

Импорт серверного модуля из клиентского компонента валит сборку — и это правильно,
ровно ради этого `server-only` и ставился. Поэтому контракт живёт отдельно:

```
lib/action-state.ts    ← типы + idleState, безопасно для клиента
lib/action-client.ts   ← authedAction, 'server-only'
```

Правило: **клиентские компоненты импортируют из `action-state`, серверные действия —
из `action-client`.**

Ошибку поймал именно `next build`; ни `tsc`, ни линтер её не видят. Это довод в пользу
того, чтобы сборка оставалась обязательным шагом CI, а не только проверка типов.

### Почему свой хелпер, а не `next-safe-action`

Библиотека даёт больше из коробки, но приносит зависимость с собственным релиз-циклом и
конвенциями, которые придётся обходить в нетипичных случаях. Сорок строк собственного кода
здесь читаются целиком за минуту и полностью подконтрольны. Если проект дорастёт до
сложных цепочек middleware — вернёмся к вопросу.

### После мутации

`revalidatePath` / `revalidateTag` в конце action. Ручной рефетч на клиенте — не наш путь.

## 6. Работа с типами

**Источник истины — схема Drizzle.** Ручных зеркальных интерфейсов не пишем.

```ts
type Service     = typeof services.$inferSelect                          // строка БД
type NewService  = typeof services.$inferInsert                          // вставка
type CreateInput = z.infer<typeof createServiceSchema>                   // вход формы
type ServiceCard = Awaited<ReturnType<typeof getServiceCards>>[number]   // выход в UI
```

Четыре разные формы одних и тех же данных — это нормально и правильно:

- **строка БД** содержит `userId`, служебные поля;
- **вход формы** содержит `priceUnit`, которого может не быть отдельной колонкой;
- **выход в UI** содержит имя автора из join и **не содержит** контактов.

Ошибка — пытаться свести их в один ручной интерфейс. Именно это произошло в прежнем
`src/types/index.ts`: там были `id: string` против `bigint` в схеме, статусы строками
против `integer`, поля `priceFrom` и `viewsCount`, которых нет в таблице. Файл активно
вводил в заблуждение и **подлежит удалению** (см. ROADMAP, этап 0).

В `src/types/` остаются только по-настоящему глобальные типы, не принадлежащие ни одному
домену. Доменные типы живут рядом со своим доменом.

## 7. Zod

Схемы пишем руками, в `features/<domain>/schemas.ts`. `drizzle-zod` не используем.

### Почему не генерация

Генерация даёт валидацию по форме таблицы. Но **вход формы структурно не совпадает со
строкой таблицы**, и в этом проекте расхождение не косметическое:

- `CreateServiceForm` отправляет массив фото — в БД это отдельная таблица
  `service_images`, а не колонка;
- `ContactSettingsForm` отправляет четыре канала с флагами видимости — в БД это
  строки в `profile_contacts`;
- «Договорная» — это флаг в форме и одновременно `null` в колонке цены.

Сгенерированные схемы пришлось бы переопределять почти в каждой форме — генерация не
окупается. Ручные схемы честно отражают, что вход формы ≠ строка таблицы.

Полный список расхождений схемы и вёрстки — в [DATA-MODEL.md](DATA-MODEL.md). Он и есть
причина, по которой **миграция схемы БД идёт нулевым этапом дорожной карты**, до первого
Server Action.

### Одна схема — один сценарий

```ts
export const createServiceSchema = z.object({ ... })
export const updateServiceSchema = createServiceSchema.extend({ id: z.coerce.number() })
```

Не одна `serviceSchema` на все случаи. Создание и редактирование отличаются набором
обязательных полей, и попытка выразить это флагами внутри одной схемы быстро становится
нечитаемой.

`FormData` отдаёт строки — числовые поля объявляем через `z.coerce.number()`.

## 8. Раскрытие контактов — решается на сервере

Продуктовое требование: контакты исполнителя видны только авторизованному пользователю
после явного действия.

Сейчас `ContactRevealButton` получает контакты пропсом и прячет их условием на клиенте.
При переходе на реальные данные это станет **уязвимостью, а не фичей**: то, что попало в
пропсы Server Component, попадает в HTML-payload страницы. Незалогиненный пользователь
прочитает телефоны из исходника страницы, не нажимая кнопку.

**Правило:** контакты не попадают в возврат query-функции для неавторизованного
пользователя. Список услуг отдаёт карточки без контактных полей вообще. Контакты
запрашиваются отдельным action по явному действию, с проверкой сессии на сервере.

Это конкретное применение правила 3.4 и причина, по которой оно сформулировано жёстко.

## 9. Открытые вопросы

### 9.1. Транзакции и драйвер БД

Проект использует `drizzle-orm/neon-http` — HTTP-драйвер Neon. Насколько известно на
момент написания, он не поддерживает интерактивные транзакции (только неинтерактивный
батч), в отличие от WebSocket-драйвера `neon-serverless` с `Pool`.

**Проверить это не удалось** — `node_modules` не установлен на момент написания документа.

**В v1 вопрос не блокирующий.** Объём v1 (каталог без откликов и отзывов) не содержит ни
одной мутации, которой требуется атомарность нескольких таблиц. Ближайший такой сценарий —
«принять отклик»: атомарно изменить статус отклика **и** статус задания. Он появляется
вместе с `responses`, уже после v1.

Частичный случай, о котором стоит помнить и в v1: создание услуги с фотографиями — это
вставка в `services` и затем в `service_images`. Сбой между ними оставит объявление без
галереи. Это неприятно, но не разрушительно и чинится повторным сохранением.

**План:** создание клиента изолировано в `lib/db/index.ts`. Если транзакции понадобятся —
переход на `neon-serverless` + `Pool` затрагивает один файл. Фактическое поведение
проверить перед реализацией откликов. Никакой код в остальном проекте на выбор драйвера
завязывать нельзя.

### 9.2. Хранилище изображений

`CreateServiceForm` использует `URL.createObjectURL` — это только локальное превью в
рамках вкладки. Реальной загрузки нет, blob-хранилище не выбрано. Решение нужно принять
до этапа 2 (см. ROADMAP).

### 9.3. Денежные типы

`price` и `budget` объявлены как `bigint`. Для цен в рублях ПМР это, вероятно, избыточно.
Нужно подтвердить намеренность выбора; альтернативы — `integer` (если суммы целые) или
`numeric` (если появятся копейки). Менять дешевле сейчас, чем после наполнения таблиц.

## 10. Что решено и не пересматривается без причины

Эти части уже сделаны хорошо, переписывать их не нужно:

- **Auth-стек** — better-auth + Drizzle adapter + middleware + плагин `admin`. Следует
  официальным паттернам, учитывает нюансы (ручные колонки плагина, повторная проверка
  валидности сессии в middleware, а не доверие одной cookie).
- **`auth-schema.ts`** — качественная схема с индексами на внешних ключах.
- **Route groups** `(auth)` / `(main)` / `admin` — чистое разделение, пересмотр не нужен.
- **UI-кит** на shadcn/radix и система дизайн-токенов.
- **Использование `headers()` и `params` как Promise** в Server Components — сделано
  верно и последовательно.
